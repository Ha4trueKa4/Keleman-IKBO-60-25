# Практическая работа 2 — Визуализатор графа зависимостей

**Дисциплина:** Конфигурационное управление · **Вариант 15**

Инструмент визуализации графа зависимостей для менеджера пакетов
**apt (Ubuntu)**. Готовые менеджеры пакетов и сторонние библиотеки для
получения зависимостей не используются — индекс репозитория скачивается
и разбирается самостоятельно. Граф обходится алгоритмом **BFS с
рекурсией**, а текстовая визуализация строится на языке диаграмм
**PlantUML**.

Работа выполняется в пять этапов; каждый этап завершается стандартно
оформленным коммитом (Conventional Commits).

## Этап 2. Сбор данных

Информация о зависимостях берётся напрямую из индекса репозитория apt —
файла `Packages` (поддерживаются `Packages`, `Packages.gz`,
`Packages.xz`). `repo_url` может быть URL или путём к локальной копии
индекса. Сам `apt` и сторонние библиотеки не используются.

Как это работает (`src/apt_repo.py`):

1. `load_index` скачивает индекс (`urllib`) и распаковывает его
   (`gzip`/`lzma`).
2. `parse_index` делит текст на записи по пустой строке и разбирает
   поля `Ключ: значение` (строки-продолжения склеиваются).
3. `find_package` выбирает запись пакета нужной версии `version`; если
   версия не задана — последнюю в индексе.
4. `direct_dependencies` собирает прямые зависимости из полей
   `Pre-Depends` и `Depends`:
   - ограничения версий отбрасываются: `libc6 (>= 2.38)` → `libc6`;
   - квалификатор архитектуры отбрасывается: `python3:any` → `python3`;
   - из альтернатив `a | b` берётся первая (как делает apt по умолчанию);
   - повторы удаляются.

```
$ ./run.sh --config examples/apt_git.ini

  libc6
  libcurl3t64-gnutls
  libexpat1
  libpcre2-8-0
  zlib1g
  perl
  liberror-perl
  git-man
```

| Пример конфига | Что показывает |
|----------------|----------------|
| `examples/apt_curl.ini`, `apt_git.ini` | прямые зависимости реальных пакетов |

## Этап 3. Основные операции

Строится полный граф зависимостей с учётом транзитивности.

### Алгоритм: BFS с рекурсией (`src/graph.py`)

Обход идёт по уровням: одна рекурсивная функция `_bfs` обрабатывает один
уровень графа, собирает следующий и вызывает себя для него.

```
_bfs(уровень, глубина):
    если уровень пуст или глубина >= max_depth: стоп
    для каждого пакета уровня:
        для каждой зависимости:
            пропустить, если имя содержит подстроку filter
            добавить ребро пакет -> зависимость
            если зависимость встречается впервые:
                запомнить её глубину и положить в следующий уровень
    _bfs(следующий уровень, глубина + 1)
```

- **Глубина.** Корень имеет глубину 0, прямые зависимости — 1 и т. д.
  `max_depth = N` раскрывает N уровней; пакеты на глубине N попадают в
  граф, но не раскрываются (помечаются `...`). `max_depth = 0` — только
  сам пакет.
- **Фильтр.** Зависимости, в имени которых есть подстрока `filter`, не
  попадают в граф и не раскрываются (сам анализируемый пакет не
  фильтруется).
- **Циклы.** Каждый пакет раскрывается ровно один раз: если зависимость
  уже есть в графе, добавляется только ребро. Поэтому цикл не приводит к
  бесконечному обходу. Найденные циклы выводятся отдельно
  (`find_cycles`, поиск обратных рёбер обходом в глубину).
- **Виртуальные пакеты apt.** Если имени нет в индексе, но его
  предоставляет другой пакет (`Provides`), строится ребро на поставщика
  с наивысшим `Priority`: `awk -> mawk`.

### Тестовый режим

При `test_mode = true` вместо индекса apt читается файл описания графа
(`src/test_repo.py`). Пакеты называются большими латинскими буквами,
одна строка — один пакет и его прямые зависимости:

```
A: B C
B: D
C: D
D:
```

Пустые строки игнорируются; строчные буквы, цифры, отсутствие `:` и
повторное описание пакета — ошибки. Относительный путь `repo_url`
отсчитывается от папки конфигурационного файла.

|----------------|-------------|----------------|

| `test_cycle.ini` | `cycle.graph` | цикл A → B → C → A |
| `test_depth.ini` | `chain.graph` | ограничение `max_depth = 2` |

## Этап 4. Дополнительные операции

Параметр `load_order = true` включает вывод **порядка загрузки**
(установки) зависимостей: каждая зависимость идёт раньше пакетов,
которым она нужна, анализируемый пакет — последним.

### Алгоритм (`src/order.py`)

Обход графа в глубину с добавлением пакета в список **после** всех его
зависимостей (post-order). Пакет помечается «в обработке», пока
обходятся его зависимости. Если обход снова приходит в такой пакет —
это цикл: ребро пропускается, и цикл разрывается. Каждый пакет попадает
в список ровно один раз.

| Пример | Порядок |
|--------|---------|
| `test_diamond.ini` | D, B, C, A |
| `test_cycle.ini` (A → B → C → A, C → D) | D, C, B, A |
| `test_filter.ini` (`filter = DEV`) | LIBC, CORE, GFX, UI, APP |

### Сравнение с apt

Сравнение выполнено настоящим apt 3.0.3 (WSL, Debian 13) на **том же**
индексе Ubuntu noble main. Скрипт `scripts/apt_compare.sh` создаёт
изолированное окружение apt во временном каталоге: только источник
Ubuntu noble main и пустой список установленных пакетов. Затем он
вызывает `apt-get install -s --no-install-recommends` — это симуляция,
ничего не устанавливается и root не нужен.

```bash
./scripts/apt_compare.sh order bash
./run.sh --config examples/order_bash.ini
```

| # | Наш инструмент | apt |
|---|----------------|-----|
| 1 | gcc-14-base | gcc-14-base |
| 2 | libgcc-s1 | libc6 |
| 3 | libc6 | libgcc-s1 |
| 4 | libtinfo6 | mawk |
| 5 | mawk | libcrypt1 |
| 6 | awk | base-files |
| 7 | libcrypt1 | libtinfo6 |
| 8 | base-files | debianutils |
| 9 | debianutils | bash |
| 10 | bash | — |

Результаты для `bash` и `curl` (`examples/order_curl.ini`):

1. **Состав реальных пакетов совпадает полностью:** у `bash` 9 из 9,
   у `curl` 32 из 32.
2. **В нашем списке есть виртуальные пакеты** — `awk`, а у `curl`
   ещё `libssl3`, `libgnutls30`, `libnettle8`, `libhogweed6`. Реальных
   пакетов с такими именами в индексе нет, это «роли» из поля
   `Provides`. apt ставит сразу пакет-поставщик (например, `mawk`), а
   само виртуальное имя не устанавливает.
3. **Порядок отличается, но оба порядка корректны.** Проверено, что и
   у нас, и у apt каждая зависимость стоит раньше зависящего от неё
   пакета, кроме одного ребра — внутри цикла `libc6 ↔ libgcc-s1`.
   Цикл нельзя упорядочить без разрыва: мы ставим `libgcc-s1` раньше
   `libc6`, а apt для `bash` делает наоборот.
4. **Почему порядок разный.** Наш инструмент выдаёт один топологический
   порядок обходом в глубину. apt устроен сложнее: он делит установку
   на распаковку (`Inst`) и настройку (`Conf`), обязан настроить
   пакеты из `Pre-Depends` до распаковки зависящего пакета, применяет
   «немедленную настройку» и собственные эвристики упорядочивания.
5. **Другие возможные расхождения в реальной системе:** apt не ставит
   уже установленные пакеты, по умолчанию добавляет `Recommends`
   (в сравнении отключено флагом `--no-install-recommends`), выбирает
   альтернативу `a | b` с учётом установленных пакетов и приоритетов
   (pinning) и учитывает ограничения версий. Наш инструмент всего этого
   не делает.

### PlantUML (`visualize.to_plantuml`)

(в именах пакетов бывают символы `+`, `.`, `-`, недопустимые в
идентификаторах PlantUML). Анализируемый пакет выделен голубым, пакеты,
не раскрытые из-за `max_depth`, — серым, ребро, замыкающее цикл, —

### ASCII-дерево (`visualize.to_ascii_tree`)

Дерево строится обходом от корня. Чтобы большие графы не разрастались
экспоненциально, каждый пакет раскрывается один раз, повторы
помечаются:

- `(*)` — пакет уже раскрыт выше;
- `(цикл)` — пакет уже есть на текущем пути от корня;
- `...` — пакет не раскрыт из-за `max_depth`.

```
bash
|-- libc6
|   `-- libgcc-s1
|       |-- gcc-14-base ...
|       `-- libc6 (цикл)
|-- libtinfo6
|   `-- libc6 (*)
|-- base-files
|   |-- awk
|   |   `-- mawk ...
|   |-- libc6 (*)
|   `-- libcrypt1
|       `-- libc6 (*)
`-- debianutils
    `-- libc6 (*)
```

### Сравнение со штатными средствами apt

Штатный инструмент визуализации apt — `apt-cache dotty` (граф в формате
Graphviz DOT); текстовое дерево даёт `apt-cache depends --recurse`.
Оба запущены на том же индексе Ubuntu noble main
(`./scripts/apt_compare.sh dotty PACKAGE`). Наш граф построен с полной
глубиной (`max_depth = 50`).

| Пакет | Наш граф: пакетов / связей | dotty: связей-зависимостей | dotty: связей-конфликтов |
|-------|----------------------------|----------------------------|--------------------------|
| bash | 10 / 15 | 13 | 27 |
| curl | 36 / 85 | 81 | 54 |
| git | 54 / 132 | 130 | 184 |

**Все связи-зависимости dotty для `bash` и `curl` есть в нашем графе.**
Для `git` отличаются три связи. Объяснение всех расхождений:

1. **Виртуальные пакеты.** dotty рисует виртуальный пакет треугольником
   и дальше его не раскрывает. Мы добавляем связь на поставщика с
   наивысшим `Priority` (`awk -> mawk`, `libssl3 -> libssl3t64`, …) и
   раскрываем поставщика. Отсюда наши «лишние» связи.
2. **Конфликты.** dotty рисует зелёным связи `Conflicts`/`Breaks`
   (их больше, чем зависимостей) и проходит по ним дальше. Так у `git`
   появились `lsb-base -> sysvinit-utils` и `sysvinit-utils -> libc6`:
   dotty дошёл до `lsb-base` по ребру `dpkg ⇢ lsb-base` (Breaks). Наш
   инструмент строит граф только по `Depends` и `Pre-Depends`.
3. **Квалификатор архитектуры.** dotty оставляет `perl:any` отдельным
   (виртуальным) узлом, мы приводим его к `perl`:
   `liberror-perl -> perl` вместо `liberror-perl -> perl:any`.
4. **Отсутствующие пакеты.** dotty показывает шестиугольниками пакеты,
   которых нет в индексе (как правило, цели конфликтов). У нас их нет,
   так как конфликты не анализируются.
5. **Pre-Depends.** dotty выделяет их синим, мы не отличаем их от
   `Depends`.
6. **`apt-cache depends`** раскрывает *всех* поставщиков виртуального
   пакета: для `<awk>` и `gawk`, и `mawk`, поэтому в его выводе есть
   зависимости `gawk` (`libgmp10`, `libmpfr6`, `libreadline8t64`, …).
   Мы, как и apt при установке, выбираем одного поставщика.
7. **Формат.** dotty выдаёт Graphviz DOT, мы — PlantUML. Ограничение
   глубины и фильтр по подстроке у dotty отсутствуют.
